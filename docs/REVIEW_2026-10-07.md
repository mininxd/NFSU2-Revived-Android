pipeline, pcrecomp runtime, existing documentation and logs; targeted inspection
of the catalog and disassembly of the analysis binary. No new game session or
compilation was performed. Execution results cited are from the saved sessions

## Input: What We Already Know

Main source: `logs/run_20261006_161815.log`.

1. DirectInput is created and the device receiving the action map achieves
   Acquire. GetDeviceData delivers repeated press (`0x80`) and release (`0x00`)
   events, with `uAppData=0x1F` and `0x22`. Therefore, it is incorrect to state
   that no input is received. The physical key for each event and its complete
   path to the frontend have not yet been identified.
2. Four BuildActionMap calls have initialized formats and return success.
   The three failed calls receive structures with size, number of actions,
   and other fields set to zero. This explains the observed invalid parameter,
   but comparison with the original is needed to determine why they are empty
   and whether they are relevant to the problem.
3. SetActionMap returns `0x0000000B` (DI_SETTINGSNOTSAVED), a documented success
   result: on its own it does not indicate the map was not applied.
   Reference: https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417919(v=vs.85)
4. Mouse failures upon losing focus are consistent with exclusive foreground
   mode. They do not by themselves explain the keyboard events received while
   frames continue to present.

### Path Located in the Binary

- EnumDevicesBySemantics callback: `0x5CA660`, calls `0x5C1080`.
- `0x5C1080`: constructs the four maps from `0x86F348`, the three additional
  empty formats, and applies the map from `0x86F490`.
- `0x5C15F0`: Poll, GetDeviceData, queries GetObjectInfo and processes keystrokes.
- `0x5C1840`: another Poll/GetDeviceData path; its read branch depends on
  `[this+0x234] == 0x13`. It then queries `0x870768` and updates masks in
  `[this+8]` / `[this+0xC]` according to `uAppData`.
- The catalog identifies `0x5CF220` as the direct caller of both paths.

These addresses are instrumentation points; they do not yet prove which branch
is active during the intro nor where the action is lost or ignored.

### Tracer Flaws Affecting Diagnostics

- The log states that DIACTIONA is 0x34 bytes, but the observed format uses
  40 bytes (0x28) on x86. It reads `dwHow` via `act[12]`; it corresponds to
  `act[9]`. The printed value falls outside the current action.
- Device detection by comparison with the mouse vtable confuses shared AddRefs:
  the log records the same IDirectInput8 object pointer as `dev1`. It can also
  omit methods from another vtable.
- It only displays the first event of each batch, limits the total to 64 records,
  and only logs events if HRESULT is exactly zero. Non-negative results with
  events must also be logged, including buffer overflows, effective element
  size, and guest caller.

## Runtime and Portability Risks

- `native32.c` saves integer registers, x87 and MMX per thread, but `regs_t`
  does not include XMM, MXCSR, or published global flags. The project adds
  XMM/MXCSR as globals. Review their preservation across thread switches and
  callbacks; this is a verifiable omission in saved state, not a proven cause
  of the keyboard issue.
- The native32 bridge and callbacks depend on MSVC x86 assembly and Windows
  exceptions. They must be replaced for ARM64.
- Compiling generated C for 64 bits is not enough: 32-bit guest pointers
  cannot store arbitrary host pointers. Guest memory, allocators, handles,
  and buffer/callback/vtable translation must be defined.
- `win32hle` already exists in pcrecomp as a portable base, but its described
  tests are synthetic 32-bit guests and its pointer allocation/passing retains
  direct uint32_t casts. It is not an out-of-the-box NFSU2 ARM64 host.
- Lifter coverage and documented tests help, but do not certify all semantics
  or subsystems that have not yet been executed.
- The D3D9 inventory only covers startup and the intro. A race will expand
  the required methods, shaders, states, and formats.
- Guest C++/SEH exceptions remain a documented pending risk.

## Recommended Order of Operations

1. **Reliable keyboard measurement on Windows.** Fix the tracer; log real device
   identity, full map, and all batch events with guest caller. Instrument the
   identified paths, context flags, masks, and action delivery to frontend.
   Compare a known sequence of Enter, Escape and arrows with the original executable
   on the same installation. Avoid assuming the three empty structures are the cause.
2. **Close a playable PC milestone.** Skip/finish intros, enter the menu, navigate,
   open garage, and run a race with steering, acceleration, and braking. Verify file
   loading, audio, saving, and focus recovery. Capture the graphical inventory of
   that session.
3. **Decouple the game from the host.** Keep Windows as reference and define APIs
   for guest memory, handles, callbacks, threads, files, timing, input, audio, and
   graphics. First preserve guest serialization until full per-thread state and
   synchronization tests are in place; removing the global lock is a later
   optimization, not a requirement to start Android.
4. **Test ARM64 in layers.** Minimal host and memory/pointer tests, dispatch, and
   callbacks before attempting the full game. Inventory used imports against real
   HLE coverage. Then integrate windowing and Android lifecycle, action-based input,
   audio, and D3D9 translation.
5. **Demonstration APK.** Reproducible startup, user installation data, menu,
   touch/gamepad controls, and a race. Measure performance and memory on real
   hardware before optimizing.
